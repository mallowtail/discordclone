# Stickers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Server admins upload stickers; any member sends them anywhere (servers, DMs, groups); everyone who can see the message sees the sticker; deleting one turns past messages into "Sticker removed".

**Architecture:** A `stickers` table + public `stickers` storage bucket, both permission-gated by a new `manage_stickers` role permission. A sticker message stores a snapshot in `messages.sticker` (jsonb, like `messages.gif`) that the database rebuilds from the sticker row on insert after checking the sender is in the sticker's server. Deleting a sticker rewrites snapshots to `{id, name, removed: true}`.

**Tech Stack:** Next.js 16 (read `node_modules/next/dist/docs/` before writing Next-specific code — see AGENTS.md), React 19, Tailwind v4 tokens, Supabase (Postgres RLS, Storage), vitest.

**Spec:** `docs/superpowers/specs/2026-11-21-stickers-design.md` — read it first.

## Global Constraints

- Files: `image/png`, `image/gif`, `image/webp` only; ≤ **524288 bytes** (512 KB); animated allowed.
- Display: at most **160 px** on the longer side.
- **30 stickers per server.**
- Names: trimmed, inner whitespace collapsed, no control characters, **2–30 characters**, unique per server ignoring case.
- Permission key `manage_stickers`, label **"Manage Stickers"**; owners always have it; backfilled onto roles that have `manage_server`.
- A sticker message has `content = ''` and no image, file, GIF, poll or forward.
- Storage path `<server_id>/<sticker_id>.<png|gif|webp>`; public URL prefix `https://dpsikhsxdwigeuyonfch.supabase.co/storage/v1/object/public/stickers/`.
- Copy: picker empty state "No stickers yet — server admins can add them in Server Settings → Stickers."; deleted sticker "Sticker removed"; reply/pin preview "Sticker"; errors "A sticker with that name already exists", "This server already has 30 stickers", "Stickers must be PNG, GIF or WebP", "Stickers must be 512 KB or smaller".
- Imports use `@/…`. Pure logic in `src/lib`, one test file per lib file in `tests/` (`src/lib/messages/stickers.ts` → `tests/stickers.test.ts`).
- Migrations are applied by hand via the Supabase Management API after a dry run; never edit an already-applied migration.

## Review Focus

1. **Deleting a server that has stickers** must still work: the cascade fires the sticker delete trigger, whose audit-log insert must not reference the vanishing server. → dry-run assertion in Task 1.
2. **Someone who left or was kicked from a server** tries to send its sticker (old picker state or crafted request) → refused with "cannot use that sticker". → dry-run assertion in Task 1, e2e in Task 6.
3. **Two uploads at once when a server has 29 stickers** → exactly one succeeds. → advisory lock in Task 1; dry-run assertion of the 31st insert failing.
4. **Animated GIF / animated WebP / APNG uploads keep animating, and transparent PNGs stay transparent** → `isAnimatedImage` tests in Task 2; Task 3 never re-encodes animated files and only re-encodes static ones to PNG/WebP.
5. **Timed-out users** can't send stickers: the picker is disabled exactly like the GIF picker (`disabled={!!timedOutUntil}`), and the DB's existing send rules still apply. → Task 4.
